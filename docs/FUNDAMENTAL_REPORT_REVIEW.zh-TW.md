# 基本面報告審查清單

*[English](FUNDAMENTAL_REPORT_REVIEW.md) · 繁體中文*

**目的**：從抓取資料到發佈頁面，列出影響 `fundamental-analysis`
報告的每個環節，讓每個部分都能單獨審查。每一節列出相關檔案、要檢查的項目，以及在實際報告中已經發現的問題。

**範例報告**：
[`/reports/amd/fundamental_analysis_2026-10-21_gemini/`](https://yennj12.js.org/finance_data/reports/amd/fundamental_analysis_2026-10-21_gemini/)
（原始檔：`ai_gen_report/fundamental/amd/fundamental_analysis_2026-10-21_gemini.md`，
75 KB、11 章、15 個 Mermaid 區塊、214 列表格）。

**已查核**：**全部 37 檔股票**各自最新的基本面報告，逐項比對 SEC XBRL 申報資料、財報與市場資料。結果見第 12 節。

## 1. 資料抓取與 context

相關檔案：`utils/data_fetch.py`、`context/__init__.py`（L312–378）、`data/prices.py`、`data/fundamentals.py`

- [ ] **🔴 單季欄位被讀成 TTM**（已在第 12 節證實）。`PROFITABILITY & GROWTH`
  區塊（`context/__init__.py:52–56`）傳入 yfinance `info` 欄位，但標籤沒說明涵蓋哪個期間。
  `revenueGrowth`、`earningsGrowth`、`operatingMargins` 都是**最近一季**的數字；
  `earningsQuarterlyGrowth` 是該季的**年增率**，標籤卻寫成「(QoQ)」。
  context 同時也列出 TTM 財報，模型就把兩者接在一起。三份報告都寫出
  「TTM 營收 …（YoY +X%）」和「TTM 營業利益率 X%」，用的卻是單季數值。
  修正方式：每個欄位標明期間，或改由我們自己從財報計算 TTM 成長率與利潤率。
- [ ] **🔴 `Free Cash Flow` 是 yfinance 的「levered FCF」**，不是營業現金流 − 資本支出
  （`context/__init__.py:70`）。TSLA：$4.84B vs $5.76B；AMD：$8.84B vs $8.40B。
  在 TSLA 和 AMD 的報告中，模型接著**自行編了一個資本支出數字**，讓 FCF
  表格能對上 yfinance 的數字。全部股票中，寫出 FCF 的 25 份報告有 18 份是錯的，
  其中 5 份的資本支出是反推出來的（12.3 節）。
- [ ] **🔴 ADR 的比率混用幣別。** TSM（TWD）和 SKHY（KRW）以美元報價，yfinance 的 `info`
  比率卻把當地幣別的現金流除以美元市值。報告印出「FCF Yield 56.25%」/「EV/EBITDA 4.08x」
  （TSM）和「FCF Yield 53.4%」/「Forward P/E 4.16x」（SKHY）。當
  `financialCurrency ≠ currency` 時，應換算數字或拿掉這些欄位。
- [ ] **🔴 SEC 基本面資料庫永遠缺少當前會計年度。**
  `fundamentals.fiscal_years()`（`data/fundamentals.py:352`）只回傳**已結束**的會計年度，
  `discrete_quarters()` 也只保留這些年度內的季度，因此進行中年度的 Q1–Q3 一律被丟掉。
  截至 2026-10-23，AMD / TSLA / PLTR 的資料停在 2025-12，但 SEC 早已有它們 2026 年的
  10-Q（TSLA 的 Q3 在 2026-10-22 申報）。每檔股票的最後一列都是上一個會計年度結束日，
  所以 Market Data 頁面最多落後三季，而 `update_fundamentals.py` 還回報「unchanged」。
- [ ] **prompt 要求、但 context 沒有提供的輸入。** 基本面分支傳入年度與季度損益表、
  年度資產負債表、年度與季度現金流量表、`info` 比率、Finviz / StockAnalysis / Roic.ai
  文字、財報、評等調整與新聞。但 prompt 還要求：
    - **同業倍數**（規則 4：「2-3 家直接競爭對手的估值倍數」；7.1 節）。我們沒有抓同業資料，
      這些數字只能來自模型記憶。AMD 範例的 8.8 節給「同業 Forward P/E (38.0x) 參考 NVDA」25% 權重。
    - **WACC 輸入**（無風險利率、股權風險溢酬、債務成本、稅率）。只提供了 `beta`。
    - **DCF 輸入**（折舊攤銷、營運資金變動、利息費用、稀釋股數）。這些都不在
      `bs_rows` / `cf_rows` 裡。
    - **歷史估值區間**（7.2 節）。我們已經在 `data/fundamentals/` 算好 P/E 區間
      （Market Data → Valuation），但 context 從未讀取這個資料庫。
- [ ] **兩個資料來源。** 報告的數字來自即時抓取的 yfinance，同一個股票頁面上的
  Market Data 分頁則來自已提交的 `data/prices` + `data/fundamentals`。
  要決定 context 是否改讀這兩個資料庫，讓報告和頁面不可能不一致。
- [ ] **讀者看不到爬蟲失敗。** Finviz、StockAnalysis 或 Roic.ai 失敗時，context 會拿到
  `(no data)`，但報告標頭仍寫「數據來源：Yahoo Finance, Finviz, StockAnalysis, Roic.ai」，
  因為這行寫死在 `fundamental.txt:90`。應該記錄實際有回傳資料的來源（放在 frontmatter
  或標頭），或拿掉這行。
- [ ] **資料被截短。** 公司簡介只取 500 字元；`df_to_text` 只傳 4 年年度、4 季季度資料，
  對一份含 5–10 年 DCF 的 11 章報告來說太短。
- [ ] **非美股與 ETF**（`0050`、`2330.TW`…）走同一個分支和 prompt。要檢查幣別、單位
  （TWD vs USD），以及 11 章的個股模板是否適用於 ETF。
- [ ] **新聞是不受信任的文字**（RSS / 爬取的標題）。見 CLAUDE.md 的 prompt injection
  說明：產生報告的模型和 QA 評審有同樣的風險。

## 2. Prompt：`prompts/fundamental.txt`

- [ ] **範例數字被模型照抄。** 規則 18（L75–76）用 `WACC = … = 9.41%` 和 `$325`
  當示範。2026-10 的基本面報告中，**795 份有 165 份**出現 `9.41%` 這個字串。
  AMD 10-18 和 10-19 的報告都寫 WACC = 9.41%，10-20 則是 10.97%。光是 2026-10-22 一天，
  36 份報告中就有 6 份用了 WACC = 9.41%（AMZN、AVAV、GOOG、NBIS、SOXQ、SPCX；12.3 節）。
  修正方式：改用明顯是符號的值（`X.X%`），或不可能出現在真實公司的數值。
- [ ] **目錄範本與實際章節不符。** 範本（L94–105）用 `...` 省略部分列。AMD 的目錄只列
  10 列，漏掉第 11 章投資建議，但內文其實有 11 章。
- [ ] **篇幅上限與必寫內容衝突。** 「7000-10000 字」（L50）要涵蓋 11 章、50 多個小節、
  每條公式都寫出來的 10 步 DCF，以及敏感度矩陣。實際報告長達 72–83 KB。
  要確認「犧牲順序」真的能確保第 11 章完整，否則就減少必寫小節。
- [ ] **Mermaid / ASCII 圖耗 token，對讀者幫助不大。** prompt 要求「大量使用」ASCII
  方框和進度條，這些常常和旁邊的表格重複（例如 AMD 的 1.1 + 1.2 + 1.4 節）。
  要決定哪些圖真的值得保留。Mermaid 也是第一階段 QA 最常見的失敗類型（`check_mermaid.py`）。
- [ ] **評級與買入區間的邏輯沒有定義。** AMD 10-21 給**買入**評級，但 MOS 只有 +9.7%，
  它自己的圖例也標成 🔴「有限偏窄」；「合理佈局買入區間」$490–550 則完全**低於**
  $552.72 的現價。prompt 應該定義評級如何由 MOS / 上行空間門檻決定。
- [ ] **分析師共識被算進「合理價值」。** AMD 8.8 節把「華爾街分析師平均目標價」放進
  加權合理價值，佔 15%，讓這個「獨立」估值有一部分是循環論證。要決定共識目標價應該
  納入三角驗證，還是只放在旁邊參考。
- [ ] **prompt 引導出無法查證的說法。** 例如市佔率（2.2 節）、TAM（9.2 節）、
  「第 39 百分位」（8.8 節），這些都不在 context 裡。應要求這類數字標明是估計值，
  就像規則 15 對 DCF 輸入的要求一樣。
- [ ] **早班時段做不到「取報告日 {today} 收盤價」。** 02:00–03:30 UTC 的 cron 在當天美股開盤前
  執行，所以 10 份日期為 2026-10-22 的報告用的是 10-21 收盤價（12.3 節第 5 點）。應由 context
  提供附上**自身日期**的價格，並在報告中寫出這個日期。
- [ ] **只針對美股的設定。** 台股也用「頂級美股投資研究分析師」這個角色。

## 3. System message：`prompts/gemini_system.txt`

- [ ] **與 prompt 矛盾**：「一次性輸出完整的 **10 章**報告」（L64）vs 11 章；
  「8000–12000 字」（L43）vs「7000-10000 字」。篇幅與結構應該只由其中一個檔案決定。
- [ ] **「絕對不要拒絕」＋「基於…專業知識進行專業推演」** 會促使模型編造資料，而不是標出
  資料缺漏。這可能是第二階段 QA 發現捏造數字的根本原因（例如 `mu` 的 TTM 營收 $90.27B），
  而且與同一檔案中的「只引用可從提供的財務數據中確認的數字」互相矛盾。
- [ ] 確認 `openai_system.txt` 做出同樣的承諾，讓備援產出的報告遵守同一套規則。

## 4. 模型與產生參數

相關檔案：`config/providers.py`、`config/__init__.py`、`utils/llm.py`

- [ ] **Temperature 0.7**（`llm.py:198,275`），但這份報告的任務是可重現的算術。
  調低應可縮小第 7 節所述的每日差異。
- [ ] **Token 上限。** 預設 32k，Gemini 上限 65,536，OpenAI 備援（`gpt-4o`）最多 16,384，

- [ ] **🔴 拒答被當成成功的報告回傳。** 最後一次拒答重試之後，`run_claude` / `run_openai` /
  `run_gemini` 只記錄「Returning last response」就回傳拒答內容（`utils/llm.py:192,265,371`），
  `run_with_fallback` 接著把它存檔。MRVL 最新發佈的報告（2026-10-22，OpenAI 備援）只有一行
  「抱歉，我無法協助滿足此要求。」runner 應該拋出例外，讓備援鏈繼續往下或讓這次執行失敗。
- [ ] **重試機制。** 檢查截斷與退化重試（`run_gemini`）多常觸發，以及重試過的報告
  是否在 frontmatter 中標示。
- [ ] **Frontmatter 是否完整。** 目前只記錄 provider 和 model。可以加上 prompt
  版本/雜湊、temperature、各資料來源是否成功，以及所用的價格，方便比較 prompt
  修改前後的報告。

## 5. 報告格式（讀者端）

- [ ] **章節架構**：1 執行摘要 · 2 公司概覽 · 3 損益表 · 4 資產負債表 · 5 現金流 ·
  6 獲利能力 · 7 相對估值 · 8 DCF · 9 催化劑 · 10 風險 · 11 投資建議。
  這個順序對讀者合理嗎？第 11 章重複第 1 章，第 8 章就佔了約三分之一篇幅。
- [ ] **執行摘要**：讀者能否在 30 秒內、不必捲過 1.0 節，就看到評級、合理價值、MOS、
  主要風險，以及「什麼會改變我的看法」？
- [ ] **重複**：同樣的重點數字（TTM 營收、FCF、MOS）出現在目錄、1.0、1.1、1.4、1.5、
  第 8 章和第 11 章。多一份副本就多一次對不上的機會。
- [ ] **表格**：🟢🟡🔴 和 ★ 評分是否一致使用？`responsive-tables.js` 是否正確把數字欄靠右？
- [ ] **語言**：確認全文繁體中文、沒有簡體字混入。Mermaid 的 quadrant 和 mindmap
  必須用英文（prompt 規則）。
- [ ] **免責聲明**：位於文末。檢查措辭是否與網站層級的免責聲明一致。
- [ ] **手機版**：寬的 ASCII 方框（AMD 8.8 節的方框超出 66 欄）和寬的敏感度表格。

## 6. 估值算術：可以用程式檢查

prompt 已經固定這些定義（規則 16 與 8.10 節），所以大部分不需要 LLM 就能確定性地檢查。

- [ ] **折溢價正負號。** AMD 10-21 寫「DCF $576.45｜現價溢價 **+4.1%**」，現價為 $552.72。
  正確值：552.72 / 576.45 − 1 = **−4.1%**，是**折價**。目錄、1.0 節和 1.5 節的 ASCII
  方框中，正負號都寫錯。
- [ ] **🔴 加權合理價值必須等於自己各項的總和。** TSLA 2026-10-22 寫
  `$147.71 + $16.43 + $42.53 + $57.36 + $60.21 = $334.34`，但各項加總是 **$324.24**。
  AMD 2026-10-22 寫 `$229.76 + $110.32 + $77.75 + $95.73 + $63.76 = $580.45`，
  加總是 **$577.32**。每一項乘積都對，錯的只有總和，而重點價值、MOS 和評級全都沿用了
  錯的總和。兩份報告的 8.10 節「複算檢核表」只複核了**情境**權重，沒有重加 8.8 節，
  卻仍把 MOS 標為 ✅ 一致。prompt 的 8.10 清單應加入「重加 8.8 節總和」這一項。
  **全部 36 份有 8.8 節的報告中，有 25 份差距超過 0.5%**（12.3 節）。其中 9 份把算出的總和換成編造的「調整」：「取穩健」、「精確微調」、「區域匯率緩衝」、「四捨五入至整數位」。
- [ ] **MOS / 上行空間**要能從合理價值與現價重算，且 1.0 節與 8.8 節一致。
  （AMD 10-21 通過：9.75% ≈ 9.7%、10.8%。）
- [ ] 8.6 節（情境）與 8.8 節（三角驗證）的**權重加總 = 100%**，且加權結果等於所寫數值。
  （AMD 10-21 通過：$612.44。）
- [ ] 敏感度矩陣每一格都要 **WACC > g**；WACC ≤ g 的格子必須寫 `N/A`。
- [ ] **所用價格 = 報告日收盤價**（`data/prices/<t>.csv`）。（AMD 10-21 通過：
  $552.72 = 2026-10-21 收盤價。）
- [ ] **推導出的資產負債數字**（淨現金 = 現金 − 負債；FCF = 營業現金流 − 資本支出）彼此一致。
- [ ] **ROIC 與 ROE 是否合理。** AMD 持有淨現金，報告 ROE 10.2%、ROIC 15.6%。
  這有可能（ROIC 排除商譽），但需要一句說明。

**建議後續**：在第一階段（`validate/__init__.py`）加入 `ARITHMETIC` 檢查類型，解析
1.0 儀表板與 8.8 節表格，重算 MOS、上行空間、折溢價正負號和權重總和。這些錯誤目前
regex 抓不到，LLM 評審也沒有標出；評審對 AMD 10-21 的判定反而把 TTM $41.31B 與
FY2023 $22.68B 說成「矛盾」。

## 7. 每次產出的穩定度（同一檔股票、連續幾天）

|------|------|------|----------|------|
| 10-18 | $528.75 | 9.41% | 加權 $612.30 | 買入 |
| 10-19 | $538.05 | 9.41% | DCF $621.50 / 加權 $618.70 | 買入 |

- [ ] 在 beta 與資本結構不變的情況下，WACC 三天內從 9.41% 變成 11.8%。同期 ROIC 從
  10.9%（10-19）變成 15.6%（10-21）。

## 12. 事實查核：每檔股票的最新基本面報告 vs 申報資料

**範圍**：查核 `ai_gen_report/fundamental/` 中 37 檔股票各自最新的一份基本面報告。其中 36 份日期為
2026-10-22，IONQ 最新的一份是 2026-08-15。每個數字都用能取得的最佳一手來源比對：

| 來源 | 股票 | 查核項目 |
|---|---|---|
| SEC XBRL `companyfacts`（10-Q / 10-K） | 24 家美國申報公司：AMD AMZN AVAV AVGO GOOG INTC IONQ KTOS META MRVL MSFT MU NVDA ONDS ORCL PL PLTR RKLB SNDK SOFI SPCX TSLA VST WDC | 價格、營收與成長率、營業利益率、FCF、8.8 節算術 |

| 只查價格與算術 | 7 檔 ETF：0050 QQQ ROBO SOXQ SOXX VTI WQTM | 價格、8.8 節算術 |

**方法**

- **TTM** = 上一會計年度 + 本年度累計 − 去年同期累計，取報告日當天或之前最新一份申報資料。
  SpaceX 的 Q3 10-Q 在 2026-10-22 申報，它的報告也正確使用了。
- **FCF** = 營業現金流 − 購置不動產、廠房及設備。
- **價格** = 報告日收盤價。02:00–03:30 UTC 時段的報告，對應的是**前一個**美股交易日。
- **8.8 節** = 報告寫出的加權合理價值，對比它自己各項「價值 × 權重」的總和。

回到原文確認，不只是 regex 比對。

### 12.3 問題類型（依出現次數排序）

1. **8.8 節總和不等於自己各項的加總：36 份中有 25 份。** 分兩種：
   - **默默加錯（17 份）。** 印出的小計都對，但總和錯，例如 META 寫
     `$340.07 + $153.10 + $110.25 + $81.50 + $83.31 = $781.02`（實際加總是 $768.23）。
     報告：2330.TW、AMD、GOOG、INTC、IONQ、KTOS、META、NVDA、ORCL、PL、RKLB、SKHY、
     SOFI、SPCX、TSLA、TSM、VST。
   - **編一個理由改寫（8 份，另 MU 為 ⚠️）。** 報告先算出正確總和，再換成別的數字：
     - AMZN：$312.29 → $304.58，「考慮保守原則…折讓」
     - AVAV：$172.13 → $176.99，「精確微調」
     - AVGO：加成「$482.19」（各項其實是 $422.19），再「下修權重後鎖定為 $416.80」
     - GRAB：$4.848 → $4.71，「區域匯率緩衝」
     - NBIS：$230.97 → $228.00，「四捨五入至整數位」
     - NU：$19.396 → $19.26，「保守調整權重尾差」
     - ONDS：$10.504 → $10.63，「四捨五入」
     - SOXX：$556.50 → $552.50，「嚴格取整」
     - MU：$1,353.31 → $1,348.60，「微調取整」

   差最多的是 PL（−12.3%）。修正後 PL 的 MOS 從 15.7% 變成 26.1%，跨過報告自己的
   🟡/🟢 區間，但它的評級是「持有/謹慎觀望」。
2. **寫出 FCF 的 25 份報告中，18 份是錯的。** context 的 `Free Cash Flow` 是 yfinance
   的數字，模型把它當成 TTM FCF 照抄。這個數字不是營業現金流 − 資本支出，可能差好幾倍：
   - VST：$37M vs $2.25B
   - NVDA：$41.8B vs $127.0B
   - GOOG：$22.7B vs $53.3B
   - META：$21.6B vs $41.0B

   也可能正負號相反：GRAB +$503M vs −$186M；AMZN $3.22B vs −$11.6B。
   **有 5 份報告接著反推出一個任何申報資料中都不存在的資本支出**，讓表格對得上：
   - TSLA：$13.84B vs $12.92B
   - AMD：$1.24B vs $1.68B
   - MU：$60.53B vs $30.71B
   - GOOG：約 $163B vs $132.4B
   - PL：約 $66M vs $93M

   NVDA 更進一步，為自己造成的落差編了解釋（「暫時性收縮…應收帳款」），而旁邊就寫著
   正確的 FY2026 FCF $96.68B。
3. **把最新一季成長率當成 TTM 成長率：28 份中 13 份，另 4 份兩種標示並存。** 這是第 1 節的
   `revenueGrowth` 標示 bug。成長率被高估 3.8 個百分點（AMZN）到 36.8 個百分點
   （AVGO：+85.5% vs +48.7%），ONDS 更高估 256 個百分點（+1,235% vs +979%）。IONQ 則相反，
   單季數字反而**低估**了 TTM 成長。報告有寫「最新季度」的地方，數字就是對的（INTC、ORCL、NU，
   以及 KTOS / PL / NBIS 的開頭句），但後三者在投資論點中又寫成「TTM YoY」。
4. **把單季營業利益率當成 TTM：22 份中 11 ❌ + 9 ⚠️。** MU 自相矛盾：它寫
   「營業利益達 $99.34B，營業利益率…80.7%」，但營收是 $133.19B，算出來是 74.6%。
5. **10 份報告用的是前一日收盤價。** 這些是 02:00–03:30 UTC 時段（MU、WDC、SNDK、SOXX、
   VTI、QQQ、SKHY、SOXQ、ROBO、WQTM），在當天美股開盤前就執行。價格本身是當時最新的收盤價，
   沒錯，但檔名日期和 prompt 的「報告日收盤價」都說是另一天。10-22 記憶體類股下跌 6–9%，
   所以 MU / SNDK / WDC / SKHY 發佈時，MOS 已經**低估** 4.2–6.5 個百分點
   （例如 SNDK 以 10-21 收盤算是 23.8%，以 10-22 收盤算是 30.3%）。
6. **財報非美元的 ADR 混用幣別（TSM、SKHY）。** yfinance 的比率把 TWD 或 KRW 的現金流除以
   美元市值。TSM 印出「FCF Yield 56.25%」和「EV/EBITDA 4.08x」；SKHY 印出「FCF Yield 53.4%」
   和「Forward P/E 4.16x」，報告接著用這些數字做論證。
7. **讓讀者看到的流程故障。**
   - **MRVL**：Gemini 失敗，OpenAI 備援連續拒答五次，`run_openai` 卻**把拒答當成成功回傳**
     （`utils/llm.py:265`：「Returning last response」；Claude 與 Gemini 的 runner 在 L192、
     L371 也一樣）。`run_with_fallback` 把它存檔，於是 MRVL 最新發佈的報告只有一行
     「抱歉，我無法協助滿足此要求。」第一階段 QA 會標出 `REFUSAL`，但那是發佈之後的夜間稽核。
   - **0050**：報告 22 次寫「現價 NT$195.00」，但這檔 ETF 的價格是 NT$106.90。NT$195 不在
     任何輸入中（價格資料庫和 yfinance 都約 NT$107）。它接近 0050 分割前的股價，很可能來自
     模型記憶，報告中所有估值數字都建立在這個錯的基準上。
   - **IONQ**：不在排程中，所以它的「最新」報告已經兩個月了。

### 12.7 查核結論

1. **模型抄得準，推導得差。** 從 context 抄寫的數字都通過；每一種重複出現的錯誤，都出在
   模型必須**自己推導**的數字（總和、FCF、成長率涵蓋的期間），或 context 標示不清的數字。
2. **大部分 ❌ 都能在我們自己的程式碼中修正：**

   | 修正 | 位置 | 可消除 |
   |---|---|---|
   | 為每個 `info` 欄位標明期間；從財報計算 TTM 成長率、TTM 利益率和營業現金流 − 資本支出 | `context/__init__.py` | 成長率（13）、利益率（11）、FCF（18）的 ❌，以及 5 個反推的資本支出 |
   | 用 Python 算出 8.8 節總和、MOS、上行空間與折溢價，或在第一階段檢查（`ARITHMETIC`） | `context/`、`validate/` | 25 個 8.8 節 ❌，以及 9 個編造的「調整」 |
   | 最後一次重試仍是拒答時拋出例外，而不是回傳拒答 | `utils/llm.py:192,265,371` | MRVL |
   | 把 ADR 的財報換算成報價幣別，或在 `financialCurrency ≠ currency` 時拿掉 yfinance 比率 | `context/` | TSM、SKHY 的比率錯誤 |
   | 印出價格自己的日期，而不是 cron 的 UTC 日期；從 prompt 拿掉「報告日收盤價」 | `fundamental.txt`、`context/` | 10 個價格 ⚠️ |
   | 把價格當成固定事實交給模型，並與價格資料庫比對 | `validate/` | 0050 |
3. **評級大多不變，重點數字卻多半是錯的。** 修正後只有 PL 的 MOS 跨過報告自己的區間。但讀者會
   從 1.0 節引用的數字（成長率、利益率、FCF、合理價值），大多數報告都有錯。
